## 2. Analyse et Correction d'ISSUE-001 (`/api/health`)

### 2.1 Cause racine
Dans `src/services/typeCatalog.ts`, la méthode `loadCatalog()` initialise le statut du catalogue à :
* `'CATALOG_READY'` lorsqu'un catalogue universel valide (> 500 items) est chargé.
* `'CATALOG_FALLBACK_CORE'` lorsque le catalogue de secours (53 items critiques) est utilisé.
* `'CATALOG_CORRUPTED'`, `'CATALOG_EMPTY'` ou `'CATALOG_UNAVAILABLE'` en cas d'anomalie ou d'échec de chargement.

Dans `server/routes/health.ts` (lignes 16-25), le handler vérifiait :
```ts
if (catalogMeta.status === 'CATALOG_LOADED') { ... }
```
Puisque le statut réel était `'CATALOG_READY'`, la condition échouait systématiquement, basculant l'endpoint en `unhealthy` avec un code HTTP 503.

### 2.2 Correction appliquée
Le handler `server/routes/health.ts` a été corrigé pour refléter fidèlement le contrat de domaine :
* **État nominal (HTTP 200, status `healthy`)** : `catalogMeta.status === 'CATALOG_READY' || catalogMeta.status === 'CATALOG_LOADED'`.
* **État dégradé (HTTP 200, status `degraded`)** : `catalogMeta.status === 'CATALOG_FALLBACK_CORE' || catalogMeta.status === 'CATALOG_DEGRADED'`.
* **État défaillant (HTTP 503, status `unhealthy`)** : tout autre statut (`CATALOG_CORRUPTED`, `CATALOG_EMPTY`, `CATALOG_UNAVAILABLE` ou `item_count === 0`).

## 3. Refactorisation de l'Architecture Serveur (`server.ts`)

Pour permettre des tests automatisés déterministes, isolés et sans interférence de ports :
1. **Extraction de `createServerApp(options)`** :
   * Fonction asynchrone retournant l'application Express configurée avec tous ses routeurs.
   * Option `includeVite: boolean` (désactivée par défaut lors des tests pour éviter le démarrage inutile du watcher Vite et de ses websockets).
2. **Fonction `startServer(port?, options?)`** :
   * Prend en charge le port dynamique `0` permettant au système d'exploitation d'attribuer un port libre disponible.
   * Retourne une interface standardisée `RunningServer` :
     ```ts
     export interface RunningServer {
       app: express.Express;
       server: import('http').Server;
       port: number;
       close: () => Promise<void>;
     }
     ```
3. **Maintien des comportements historiques** :
   * Détection de module principal via `isMainModule` (`server.ts` ou `server.cjs`).
   * Démarrage automatique sur le port 3000 en mode normal (`npm run dev` / `npm start`).
   * Conservation absolue de tous les exports existants (`generateOAuthState`, `logEvent`, etc.).

## 4. Nouveaux Harnais de Tests Implémentés

### 4.1 Suite d'Intégration API (`server/__tests__/api_integration.test.ts`)
Exécutable via `npm run test:api`.
Couvre **15 assertions majeures** sur serveur actif :
* **`/api/health`** :
  1. Retourne HTTP 200 et `status: 'healthy'` en condition nominale (20 526 items).
  2. Vérification d'observabilité : présence de `uptime_seconds`, `memory`, `catalog`, `sso`.
  3. Sécurité : vérification stricte de non-divulgation de secrets (ni clé ni valeur secrète SSO).
  4. Retourne HTTP 200 et `status: 'degraded'` lors de l'activation du fallback core.
  5. Retourne HTTP 503 et `status: 'unhealthy'` en cas de corruption ou d'indisponibilité du catalogue.
* **`/api/types`** :
  6. `/api/types/status` : validation des métadonnées (version, checksum, count).
  7. `/api/types/all` : validation de la structure `{ metadata, types }` et des en-têtes HTTP canoniques (`X-Catalog-Status`, `X-Catalog-Count`, etc.).
  8. `/api/types/all?format=flat` : validation du format brut en tableau JSON.
  9. `/api/types/lookup/34` : résolution exacte du type 34 (Tritanium, volume 0.01 m³).
  10. `/api/types/search?q=trit` : recherche textuelle non vide contenant Tritanium.
* **`/api/markets`** :
  11. `/api/markets/:regionId/history` : rejet HTTP 400 strict avec `{ error: 'type_id is required' }` si `type_id` est absent.
* **`/api/auth`** :
  12. `/api/auth/config` : exposition de la configuration publique sans secret.
  13. `/api/auth/url` : génération d'un token d'état CSRF cryptographique (64 caractères hex / 32 octets).
  14. `/api/auth/url` avec redirect externe non autorisé : blocage HTTP 400 strict (`INVALID_REDIRECT_URI`).
* **`/api/character`** :
  15. `/api/character/:id/orders` & `/api/character/:id/wallet` : rejet HTTP 401 strict en cas d'absence du header Authorization.
* **`/api/universe`** :
  16. `/api/universe/location/:id` : fallback déterministe pour stations ou structures non authentifiées.

### 4.2 Smoke Test Serveur (`server/__tests__/server_smoke.test.ts`)
Exécutable via `npm run test:smoke`.
Vérifie le cycle de vie complet :
1. Démarrage de l'application sur un port éphémère (`0`).
2. Vérification que le serveur écoute activement sur un port valide.
3. Émission d'une requête HTTP `GET /api/health` et assertion du code 200 et du statut sain.
4. Déclenchement de l'arrêt gracieux (`instance.close()`).
5. Vérification rigoureuse de la libération du port : une tentative ultérieure de connexion vers ce port est immédiatement rejetée (`ECONNREFUSED` / fetch failure).
6. Durée d'exécution totale : **~400 ms** sans aucun timer résiduel ni processus orphelin.

## 7. Limites Identifiées et Risques Restants (Transmis aux Lots Ultérieurs)

1. **Proxy Marché ESI (`/api/markets/*`)** :
   * Les tests d'intégration valident actuellement les rejets de validation (ex: paramètre `type_id` manquant).
   * L'interaction complète avec les upstream ESI réels nécessite la mise en place d'un intercepteur/mock ESI standardisé (hors-ligne) qui sera développé dans **LOT-003** (Hardening ESI).
2. **Gestion des sessions SSO en mémoire** :
   * Les états CSRF OAuth sont stockés dans une `Map` en mémoire dans `server/utils/authUtils.ts` avec un TTL de 10 minutes. Cette solution est adaptée à une instance unique, mais devra être revue si le déploiement évolue vers du multi-instance horizontal.
3. **Composants Frontend et Bundle initial (ISSUE-002, ISSUE-006)** :
   * Préservés sans modification conformément au mandat strict de stabilité.
